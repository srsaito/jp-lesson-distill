## Where we left off (2026-09-17 — jld-hc9.1, the model pin and the thinking level, DONE)
- **The model is pinned: `gemini-3.1-pro-preview` (ADR-0006).** A probe resolved `gemini-pro-latest` to exactly that on 2026-09-17; the same alias served 2.5 Pro when this pipeline was built. `DEFAULT_MODEL` in `gemini.py` is now the only Gemini id anywhere in the source (a test enforces that), so the CLI and `Config` cannot drift apart, and `moments.json` finally records the name of an actual model rather than of an alias.
- **Every call now reports the version the API served — but only when it differs from the id asked for.** With the pin that line never prints. With `--model gemini-pro-latest` it names the resolution, which is the one thing no artifact on disk has ever recorded.
- **Pass A sends `thinking_level=medium`, NOT `low` — the issue's premise was wrong and the measurement says so (ADR-0007).** "Transcription is mechanical, so turn thinking down" is right about transcription and wrong about Pass A, because Pass A also decides **who spoke**, and that is inference. Three `low` runs over one real 20-minute window (2026-08-17 w1, the lesson with blind ground truth) got **6 of 15** address-form cue lines wrong, against **5/5** for the 2026-08-20 run that later scored 89%. One `medium` run got 4/5.
- **The `low` misses are not subtle and not the merged-turn defect.** They are short, cleanly split lines that can only be the student — 「そそ先生は、あ、韓国に行ったことがありますか？」, 「私はもう予定はありませんけど、あー、妻が予定があります。」 — labelled `teacher`. `medium`'s single miss *is* a merged fragment, i.e. `jld-beb`.
- **Everything else was equal, which is what made the canary readable.** Coverage 100% at every level, density inside the known-good 4.6–9.6/min band, dead time 0, and no sign of fluency drift: student filler rate 13.0–18.7 per 1,000 characters against the reference's 13.7, student character counts within 6%. **Every gate except the canary passes the bad arm** — the same thing `jld-86b` was built for.
- **`medium` is not "think harder", it is slightly less than the status quo.** A patient no-retry probe put the model's own default at **11,507 thinking tokens** (first byte 71 s, complete 109 s); `medium` is 9,262 (first byte 59 s, 98 s); `low` is so cheap the API reports **no thinking count at all** and starts streaming in **4 s**. That last fact is why `None` has to read as *unknown*: a missing field taken as zero would have "confirmed" a setting that may have done nothing.
- **Cost of the choice: ~50 s per window.** A clean lesson is ~5 min of wall clock, against ~30 for the hour-long call this replaced.
- **`MINIMAL` is not an option**: `400 INVALID_ARGUMENT — Thinking level MINIMAL is not supported for this model`. The CLI offers `low|medium|high|model-default` only (`--pass-a-thinking`, Pass A only; detect and Pass B always use the model default).
- **A logging bug found the hard way:** our own diagnostics were block-buffered when a run is redirected to a log, so "the stream went quiet, retrying" sat in a 4 KB buffer until the process exited. A window that was retrying four times looked like one silent 20-minute hang. Every print in `gemini.py` now flushes.
- **The intermittent stall is NOT a thinking-level effect** and this change does not fix it. It hit the model default and `medium` on a 20-minute window today, and 2 of 4 default-level calls on the synthetic lesson; `low` saw none in three, which at n=3 means nothing. Same `jld-hc9.3` stall, same `_with_retry` handling it.
- **Free calibration data for `jld-hc9.3.3`, and it says DON'T RAISE the timeout.** Healthy first byte on a 20-minute window is **4 s at `low`, 59 s at `medium`, 71 s at the model default**, against a 300 s idle timeout. A patient probe at `medium` (no retry, 1500 s tolerance) did eventually answer at **347.8 s** — past the watchdog, which looks like proof 300 s is too tight, until the third number: it returned **5,769 chars against the healthy run's 15,787** on the same window. About a third: the silent-compression shape ADR-0005 exists to prevent. The slow call was not slow-but-good, so a re-roll beats waiting. If anything the data supports tightening toward ~120–180 s. (n=1 on the slow call, and the probe didn't keep the transcript to score — noted on the issue.)
- The measurement is committed as `tests/fixtures/thinking_level_20260917.json` + `tests/test_thinking_level_measurement.py` (counts and timings only — public repo). 129 offline tests.
- **Two follow-ups filed.** `jld-onu`: settle `low` vs `medium` with `distill label` blind clips rather than a 5-cue canary, and measure the merged-turn rate at the same time (`medium` produced 145 segments where the reference produced 192 — it may be trading a diarization defect for `jld-beb`). `jld-5vz`: the smoke test's planted *uncorrected* error 「面白いでした」 now comes back normalised as 「面白かったです」 — 0/4 at `low` and 1/4 at the model default, so it is model drift, not a level effect, and a gate that has quietly stopped gating.

## Where we left off (2026-09-06 — jld-hc9.3, the two stream-time aborts, DONE)
- **A Pass A call can no longer hang for half an hour, and can no longer spend its whole output budget repeating itself.** Both halves shipped, and the epic's remaining blocker is now only `jld-hc9.1`.
- **The stall was configuration, not a missing watchdog — the issue's own premise was wrong and the design note caught it.** The SDK turns `HttpOptions(timeout=<ms>)` into one per-request scalar, httpx expands a scalar to all four fields, and httpx's *read* timeout is the maximum gap **between chunks**, not a budget for the response. So `30*60*1000` said precisely "tolerate half an hour of silence". `STREAM_IDLE_TIMEOUT_S = 300` replaces it (`--stream-timeout`), and `httpx.ReadTimeout` was already retryable, so the whole fix is a constant. **No thread, no watchdog.** The rejected alternative is pinned by a test: per-field httpx timeouts are useless here because with `http_options.timeout` unset the SDK passes an explicit `None`, which httpx reads as *no timeouts at all*.
- **The 300 s default is provisional and deliberately generous** — nobody has measured how long a healthy audio+`response_schema` call waits before its first chunk, and thinking tokens are not answer text, so a window that is thinking looks exactly like one that has died. Every call now logs `first byte Xs, longest gap Ys`; `jld-hc9.3.3` tightens it from a real lesson's three windows. First data (34 s synthetic lesson): first byte **8.3 s** for audio, **11.6 s** for a text-only call, and in both the longest gap *equalled* the first byte — once a response starts it arrives in a couple of chunks. If that holds at 20 minutes, this is a first-byte timeout and nothing else.
- **The loop detector is the half that needed real code**, because a loop *streams continuously* — no timeout of any kind would ever fire. `find_repetition_loop` checks the tail after every chunk and fires **60 characters** into the 2026-07-29 loop, which went on to emit **58,356**.
- **The floor is calibrated, not guessed.** Real speech reaches 5 consecutive repeats (そう/はい/うん are genuine backchannels); the threshold is 20 repeats of a unit up to 64 chars. Swept over **all 53 transcript files on disk: zero false positives**, including the healthy 35-minute prefix of the very call that looped.
- **No second retry path**, deliberately: `_transcribe_window`'s `--window-attempts` already re-rolls warmer, and a warmer re-roll is exactly what breaks a degenerate decode. A window whose every attempt loops now fails loudly with resume instructions — a loop leaves no partial transcript to promote — and names a **shorter** `--window-minutes` as the lever, never `--window-minutes 0`.
- **`MAX_TOKENS` is named instead of crashing**: `OutputBudgetExhausted` reports the thinking/answer split (the historical case spent 62,911 tokens thinking and had 2,563 left for the transcript) where it used to surface as "Invalid JSON: EOF while parsing". Not retried — a window too big to fit will not fit on a second try. `thinking_budget` deliberately *not* restored from the old patch; it is a no-op on 3.x and `thinking_level` is `jld-hc9.1`.
- Failed responses are kept as `work/<date>/pass_a_partial_*.json` on both failures — which is how the loop fixture these tests run against came to exist.
- 102 offline tests. Smoke test passes end-to-end (both planted errors recovered verbatim). The vault skill's manual stall-recovery callout is rewritten and committed (Obsidian Git picked it up in `9746cc3`).

## Where we left off (2026-08-21 — Pass A sanity gates, jld-hc9.4)
- **`quality.py` gates every Pass A window** before accepting it, and re-rolls a failing window at a higher temperature (`--window-attempts`, default 2). Failed attempts are kept as `transcript_w<NN>.attempt<N>.json`; if all attempts fail, the least-bad one is promoted loudly instead of killing the run. Every window now prints one stats line, so degradation is visible in the log.
- **The threshold in the original issue was wrong and the measurement says so.** Segments-per-minute does NOT detect degradation: the known-bad 2026-08-17 single-pass run is 7.0/min, *inside* the 4.6–9.6/min range of known-good windows (chars/min is no better: bad 177, good 162–205). What separates them is **coverage** (89% vs 100%), **dead time** (8.1 min of audio behind under 1 char/s vs 0 min) and **max span** (361 s in one segment vs ≤74 s). Density is now logged, never gated.
- **Duplicates only warn.** In the bad run they are the failure mechanism — four consecutive lines from 11:13–13:04 re-emitted verbatim at 20:12–21:03, i.e. the model lost its place and replayed an earlier block over eight minutes of real audio. But the 2026-07-07 run's 11 duplicates are three passes over one textbook dialogue (「木村さん、ネットでパソコン買ったことありますか？」), a genuine drill. They look structurally identical; coverage and dead time are what tell them apart.
